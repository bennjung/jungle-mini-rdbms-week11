### 파일시스템 조건

측정 데이터는 tmpfs에 두었습니다. 리포지토리 디스크에서 같은 삽입 경로를 200행 측정한 결과는 다음과 같습니다.

| 저장 위치 | `allocate_next_id` | `append_row` | 행당 합계 | 100만 건 추정 |
|---|---:|---:|---:|---:|
| 리포지토리 디스크 | 5.72 ms | 5.50 ms | 11.22 ms | 약 187분 |
| tmpfs | 0.10 ms | 0.04 ms | 0.14 ms | 약 2.3분 |

행마다 메타 JSON과 CSV에 각각 `fsync`가 걸립니다. 디스크에서는 이 동기화가 삽입 시간을 지배해 100만 건을 한 번에 넣기 어렵습니다. 그래서 삽입·조회 모두 tmpfs에서 수행했습니다.

**따라서 삽입 시간 0.179 ms/행은 디스크 환경의 절대값이 아닙니다.** 인덱스 대 선형 조회 비교는 파일시스템 종류와 무관하게 성립합니다.

### 측정 경계

- 삽입은 `run_sql_file()`로 생성한 INSERT SQL 100만 문장을 실행했습니다.
- 조회 시간은 **`execute_query()` 호출 구간만** 측정했습니다. SQL 파싱은 타이머 밖에서 문장별로 1회 수행했습니다.
- `insert`와 `query`는 **별도 프로세스**입니다(요구사항 §6.4).
- `query` 프로세스는 시작할 때 인덱스를 다시 구축하며, 구축 시간은 조회 측정과 분리했습니다.
- 워밍업 2회는 측정값에서 제외하고 7회를 측정했습니다.
- `p95`는 nearest-rank입니다. 표본 7개에서 `ceil(0.95 × 7) - 1 = 6`번째 값, 즉 최댓값입니다.

## 5. 해석

### 등호 조회

같은 1건을 찾는 데 인덱스는 레코드 1개를 읽고, 선형 경로는 100만 개를 읽습니다. 중앙값 기준 약 124,900배 차이입니다.

### 범위 조회

100건을 찾는 데 인덱스는 100개만 읽습니다. 선형 경로는 여전히 100만 개를 읽습니다. 약 2,190배 차이입니다. 등호보다 배수가 작은 이유는 인덱스 경로도 결과 100건을 읽고 파싱해야 하기 때문입니다.

### 방문 노드 수가 4인 이유

`max_keys = 128`이면 노드 하나가 최대 129개 자식을 가질 수 있습니다. 그런데 분할은 `p = len // 2`에서 일어나므로 노드가 평균 절반만 찹니다. 실제 팬아웃은 약 65이고, 리프가 약 15,500개 생겨 내부 단계가 하나 더 필요합니다.

| 단계 | 개수(근사) |
|---|---:|
| 리프 | 15,500 |
| 내부 (1단계 위) | 238 |
| 내부 (2단계 위) | 4 |
| 루트 | 1 |

따라서 루트 → 내부 → 내부 → 리프로 4개 노드를 방문합니다. 이론적 최소 깊이(3)보다 하나 깊은 것은 분할 후 노드가 절반만 차기 때문입니다.

### 범위 조회의 방문 노드 6

하강 4개에 리프 이동 2개가 더해집니다. 리프 하나에 약 64~65개가 들어 있어 100건은 리프 2개에 걸칩니다.

### 전체 조회

인덱스를 쓰지 않는 기준선입니다. 선형 경로와 같은 5.6초대이며, 차이는 측정 잡음 수준입니다.

## 7. 한계

- 삽입 시간은 tmpfs 기준입니다. 디스크 환경의 삽입 처리량은 위 표의 추정치를 참고해야 합니다.
- 단일 프로세스 환경입니다. 동시성과 다중 프로세스는 요구사항 §2.2에서 제외되어 있습니다.
- 인덱스는 프로세스마다 다시 구축합니다. 실행 시작 비용에 5.54초가 더해집니다.
- 인덱스 노드는 파이썬 객체입니다. 100만 건에서 메모리 사용량은 별도로 측정하지 않았습니다.
- `ORDER BY`가 없으므로 결과 순서는 계약이 아닙니다(요구사항 §3.5).
