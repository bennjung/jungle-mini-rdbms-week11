## 1. 목표와 완료 기준

Phase 2는 **B+ 트리 인덱스의 정확성**과 **SQL 조회 성능 차이**를 모두 증명해야 완료된다.

| 판단 축 | 완료 기준 | 증거 |
|---|---|---|
| 자료구조 정확성 | 삽입·검색·범위 조회가 노드 분할 후에도 올바르다 | B+ 트리 단위 테스트 |
| SQL 연동 정확성 | 기존 SQL 의미를 유지하고, `id` 조건에서 인덱스 경로를 사용한다 | 실행기·저장소 통합 테스트 |
| 인덱스 사용 증명 | `id` 조회가 전체 CSV 읽기(`read_rows`)를 호출하지 않는다 | 호출 spy 테스트 |
| 성능 | 100만 건 이상에서 등호·범위·전체 조회를 측정해 보고한다 | 벤치마크 결과 문서 |

성능은 **절대 배수 합격선을 두지 않는다.** 측정값, 접근 경로, 방문 노드 수, 읽은 레코드 수를 함께 보고하고 차이를 분석한다.

## 2. 범위

### 2.1 포함

- 자동 증가 `id`를 키로 하는 메모리 기반 B+ 트리
- CSV 레코드의 **시작 바이트 위치**를 인덱스 값으로 저장
- 저장소 시작 시 CSV에서 인덱스 구축
- `INSERT` 시 인덱스에 새 `id` 등록
- `id` 등호 및 범위 조건의 인덱스 조회
- `AND`로 연결된 여러 `id` 조건의 범위 교집합
- `id` 조건과 다른 필드 조건이 함께 있을 때, 인덱스로 후보를 좁힌 뒤 나머지 조건 적용
- 100만 건 이상 데이터 삽입 및 성능 측정
- 인덱스 사용 여부를 확인할 수 있는 통계

### 2.2 제외

- `DELETE`, `UPDATE`, `CREATE TABLE`
- `ORDER BY`
- `JOIN`
- 인덱스 파일 영속화
- 디스크 기반 B+ 트리 노드
- `id` 이외 컬럼의 인덱스
- 복합 인덱스
- 동시성 제어 및 다중 프로세스
- 트리 노드 삭제·병합(underflow 처리)

## 3. 인덱스 모델

### 3.1 키와 값

| 항목 | 확정 내용 |
|---|---|
| 키 | 자동 증가 `id` (`INT`, 중복 없음) |
| 값 | 해당 레코드가 시작하는 **CSV 파일의 바이트 위치** |
| 노드 위치 | 메모리 |
| 원본 데이터 | CSV 파일 (파일이 유일한 원본) |
| 인덱스 수명 | 프로세스 실행 중에만 유지, 종료 시 소멸 |

`id`는 0부터 증가하며, 저장 실패로 번호가 비어도 허용한다. 음수 `id`가 CSV에 있으면 그대로 인덱싱한다.

### 3.2 구축 시점

- `CsvTableStorage` 생성 시 **모든 테이블**의 CSV를 스캔해 인덱스를 구축한다.
- 기존 `next_id` 보정 스캔과 같은 시작 시점에 수행한다. 두 스캔을 한 번으로 합칠지는 설계 단계에서 정한다.
- 인덱스 구축 시간은 조회 성능 측정에서 제외하고 별도로 보고한다.
- 인덱스는 파일로 저장하지 않으며, 재실행 시 다시 구축한다.

### 3.3 삽입

1. Phase 1 경로로 `id`를 발급하고 CSV에 레코드를 추가한다.
2. CSV 추가가 성공한 뒤, 새 레코드의 시작 바이트 위치를 B+ 트리에 등록한다.
3. CSV 추가가 실패하면 인덱스에 항목을 추가하지 않는다.

### 3.4 조회 경로

| `WHERE` 조건 | 접근 경로 |
|---|---|
| `id = 값` | B+ 트리 탐색 → 해당 레코드 1건 읽기 |
| `id` 범위 (`<`, `<=`, `>`, `>=`) | B+ 트리로 시작 위치 탐색 → 조건에 맞는 레코드만 읽기 |
| 여러 `id` 조건의 `AND` | 범위 교집합으로 후보 축소 |
| `id` 조건 + 다른 필드 조건 | 인덱스로 후보를 찾은 뒤 나머지 조건을 검사 |
| `id != 값` | 인덱스 미사용, 기존 선형 탐색 |
| `id IS NULL`, `id IS NOT NULL` | 인덱스 미사용, 기존 선형 탐색 |
| `id` 조건 없음 | 인덱스 미사용, 기존 선형 탐색 |

인덱스 경로는 **전체 CSV 읽기(`read_rows`)를 호출하지 않아야 한다.**

### 3.5 결과 순서

- Phase 2부터 **`ORDER BY` 없는 `SELECT`의 행 순서는 보장하지 않는다.**
- 이는 상용 DBMS의 동작과 같은 계약이며, 현재 구현이 우연히 CSV 순서를 반환하더라도 이를 계약으로 삼지 않는다.
- `format_result()`는 **입력으로 받은 행 순서를 그대로 출력**하는 책임을 유지한다. 이는 SQL 결과 순서 보장과 별개다.

## 4. 정확성 계약

| 항목 | 확정 내용 |
|---|---|
| 빈 테이블 | 인덱스도 비어 있고, `id` 조건 조회는 0건 |
| 중복 `id` | 인덱스 구축 시 `StorageError`로 거부 |
| `id` 값 누락 | 허용 (자동 증가 번호가 비어도 됨) |
| 음수 `id` | 허용, 그대로 인덱싱 |
| 경계값 | `>=`, `<=`는 포함, `>`, `<`는 제외 |
| 다중 `id` 조건 | 모든 조건을 만족하는 교집합만 후보로 사용 |
| UTF-8 | 바이트 위치는 UTF-8로 인코딩된 파일 기준 |
| 따옴표 안 개행 | 레코드 경계 계산 시 문자열 내부 개행을 레코드 구분자로 오인하지 않음 |
| 손상된 CSV | Phase 1과 동일하게 `StorageError` |
| CSV 없음 | `StorageError`, 파일 자동 생성 없음 |
| 동시성 | Phase 1과 동일하게 단일 프로세스 전제 |

중복 `id`는 정상 `INSERT` 경로에서는 발생하지 않는다. 파일 직접 편집이나 외부 복사로만 발생할 수 있으며, 이 경우 시작 시 거부한다.

## 5. Phase 1 계약 변경

### 5.1 결과 순서 보장 폐기

Phase 2에서 `ORDER BY` 없는 `SELECT`의 행 순서 보장을 공식적으로 폐기한다. 이에 따라 다음 기존 테스트의 다중 행 순서 단언을 **순서 비의존 비교**로 조정한다.

| 파일 | 테스트 |
|---|---|
| `tests/test_executor.py` | `test_b_s_01_select_star_returns_all_columns_and_rows` |
| `tests/test_executor.py` | `test_b_s_02_select_columns_preserves_requested_order` |
| `tests/test_executor.py` | `test_b_s_14_is_not_null_on_non_nullable_column_returns_all` |
| `tests/test_executor.py` | `test_b_s_15_duplicate_columns_are_allowed` |
| `tests/test_executor.py` | `test_b_s_26_where_column_can_be_outside_output_columns` |

- 컬럼 순서(`result.columns`)는 계속 보장한다.
- `format_result()`의 입력 행 순서 보존 테스트는 변경하지 않는다.
- Phase 1 문서에 “`ORDER BY` 없이는 행 순서를 보장하지 않는다”는 설명을 추가한다.

### 5.2 유지되는 Phase 1 계약

- `INSERT` 문법과 `id` 자동 증가
- `SELECT` 컬럼 선택, `WHERE` 비교·`IS NULL`·`AND`
- 자료형 검증과 `NULL` 처리
- CSV 형식과 메타데이터 규칙
- `next_id` 영속화와 재실행 시 보정
- 오류 시 후속 SQL 중단 및 선행 `INSERT` 유지
- 단일 프로세스 전제

## 6. 성능 측정 계약

### 6.1 데이터

- 대상 테이블: `registrations`
- 레코드 수: **1,000,000건 이상**
- 생성 값:
  - `id`: 0부터 자동 증가
  - `student_id`: `1000 + i` (행마다 고유·연속)
  - `course_id`: `i % 300`
  - `status`: `'APPLIED'`
- 삽입 경로: Phase 1의 `run_sql_file()`을 그대로 사용해 `INSERT` SQL을 실행한다.
- 벤치마크 전용 합성 데이터임을 결과 문서에 명시한다.

### 6.2 측정 경계

- 조회 시간은 **`execute_query()` 실행 시간만** 측정한다.
- 파싱, 표 포맷팅, 터미널 출력, 파일 생성 시간은 제외한다.
- 인덱스 구축 시간은 별도로 측정해 보고한다.
- 삽입 시간도 별도로 측정해 보고한다.

### 6.3 측정 시나리오

| 시나리오 | 인덱스 경로 | 선형 경로 | 결과 건수 |
|---|---|---|---:|
| 등호 | `WHERE id = 500000` | `WHERE student_id = 501000` | 각 1건 |
| 범위 | `WHERE id >= 500000 AND id < 500100` | `WHERE student_id >= 501000 AND student_id < 501100` | 각 100건 |
| 전체 조회 | 없음 | `SELECT id FROM registrations` | 1,000,000건 |

- 등호·범위는 같은 결과 건수를 갖도록 데이터를 구성한다.
- 전체 조회는 인덱스 비교 대상이 아니라 **전체 스캔 기준선**으로 보고한다.

### 6.4 반복과 보고

- 조회 프로세스는 삽입 프로세스와 분리한다.
- 워밍업 2회 후 측정 7회를 수행한다.
- 보고 값: 최소, 중앙값, p95, 결과 건수, 접근 경로, 방문 노드 수, 읽은 레코드 수
- 추가 보고: 100만 건 삽입 시간, 인덱스 구축 시간, 측정 환경(Python 버전, CPU, 메모리, 디스크)
- 성능 합격/불합격 배수는 두지 않고, 측정값과 해석을 함께 기록한다.

### 6.5 환경 실측 참고치

아래 값은 이 저장소의 현재 구현과 개발 환경에서 측정한 참고치다. Phase 2 구현 후 공식 결과는 별도 벤치마크 문서에 기록한다.

| 측정 | 결과 |
|---|---:|
| `read_rows()` 100만 건 | 약 4.2초, 추가 메모리 약 333MB |
| 현재 저장소 삽입 경로 | 약 0.17ms/건, 100만 건 약 2.9분 |
| Phase 1 SQL 경로 삽입 | 10만 건 22.4초, 100만 건 약 3.7분 |

## 7. 인덱스 사용 증명

### 7.1 테스트 증거

- `id` 등호 조회가 `read_rows()`를 호출하지 않는다.
- `id` 범위 조회가 조건에 맞는 레코드만 읽는다.
- B+ 트리 검색이 호출되었음을 spy 또는 통계로 확인한다.
- 비인덱스 조회는 기존 `read_rows()` 경로를 유지한다.

### 7.2 벤치마크 증거

- 각 조회의 접근 경로(`index`, `range`, `linear`, `full_scan`)를 출력한다.
- 방문 노드 수와 읽은 레코드 수를 출력한다.
- 결과 건수와 소요 시간을 함께 출력한다.

## 9. 설계 단계에서 확정할 항목

아래 항목은 요구사항이 아니라 **설계 결정**이므로, `docs/phase2-design.md`에서 사용자와 합의해 확정한다.

1. B+ 트리의 노드 구조와 최대 키 수(차수)
2. 테스트에서 노드 분할을 강제하기 위한 작은 차수 설정 방법
3. 리프 노드 연결 방식과 범위 조회 알고리즘
4. 저장소 인터페이스에 추가할 바이트 위치 조회·범위 조회 메서드
5. 실행기에서 인덱스 경로를 선택하는 조건 판정 위치
6. 조회 통계를 전달하는 인터페이스 형태
7. 인덱스 구축과 `next_id` 보정을 한 번의 스캔으로 합치는 방법
8. 벤치마크 스크립트의 CLI 옵션과 결과 출력 형식
9. 파일별 테스트 ID와 세부 기대값

| 10 | 중복 `id` | 시작 시 `StorageError` | 정상 경로에서 발생하지 않는 손상 데이터 거부 |
| 11 | 측정 경계 | `execute_query()`만 | 인덱스 vs 선형 탐색을 공정하게 비교 |
| 12 | 합격 기준 | 절대 배수 없이 수치 보고 | 환경 변동을 숨기지 않고 측정값과 해석을 제시 |
| 13 | 벤치 데이터 | `student_id` 고유·연속 | 등호 1건, 범위 100건으로 결과 건수를 맞춤 |
| 14 | 문서 위치 | `docs/phase2-*.md` | Phase 1과 같은 문서 규칙 유지 |

## 11. 최종 판단

**지금 구현을 권장한다.**

- 필수 과제이며, Phase 1 SQL 처리기를 그대로 사용해 연동할 수 있다.
- 현재 저장소의 삽입 경로가 이미 `next_id`를 영속화해 100만 건 삽입이 현실적이다.
- 비인덱스 전체 조회가 약 4.2초로, 인덱스 조회와의 차이를 측정할 여지가 충분하다.
- MVP는 “`id` 등호·범위 인덱스 + 100만 건 벤치마크 + 정확성 테스트”로 제한한다.
- 인덱스 파일 영속화, 삭제, 복합 인덱스, 동시성은 Phase 2 범위에서 제외한다.
